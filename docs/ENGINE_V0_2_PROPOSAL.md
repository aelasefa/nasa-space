# LUNA-01 engine v0.2 proposal

Draft for engine review. The current builder uses v0.1. None of the options or events below are active in v0.1. The proposed display types are in [contracts.ts](../frontend/src/app/contracts.ts), under `EngineV02Proposal`.

## Candidate catalog

Each approved option needs a stable ID, source and revision, conditions of measurement, units, assumptions, and a record of how any derived or illustrative parameter was produced. Cost and score are game abstractions and should be calibrated and labeled as such. An engineering reference establishes a principle or design example; it does not validate the game’s numerical parameters. Unsupported parts should never reach the selectable catalog.

| Slot | Candidates for evaluation | Required parameters and compatibility |
|---|---|---|
| Bus | Compact, standard, expanded platform | Dry mass, available volume and mounts, payload allowance, baseline load; exclude builds that exceed interface or launch limits. |
| Solar | Body-mounted, deployable wings, articulated arrays | Usable generation vs. illumination, angle and deployment state; require suitable mounts, voltage and controller. |
| Battery | Light pack, standard pack, extended pack | Usable energy vs. temperature and allowable depth of discharge, peak delivery, charge limits; match controller and peak load. |
| Propulsion | Cold gas, chemical monopropellant, electric | Wet/dry mass, thrust, impulse, power and burn duration; check each route's timing and maneuver requirements as well as total delta-v. Cold gas may be viable only for corrections; electric cannot be assumed to execute an impulsive insertion. |
| Communications | Low-gain antenna, patch array, high-gain dish | Band, link margin, rate, radio draw, pointing and ground network; test command coverage separately from science return. |
| Science | Mapping camera, reflectance spectrometer, neutron spectrometer; later thermal radiometer and laser altimeter | Illumination, footprint, power, pointing, data rate, calibration and observation conditions. Permit several instruments only inside bus, power and storage limits. Record evidence by instrument. A neutron hydrogen signal is indirect, terrain and temperature provide context, and a reflectance instrument needs enough usable light. |
| Thermal | Passive insulation and coatings, thermostatic heaters, enhanced heat rejection | Thermal limits and segment heat balance; account for heater power, radiator orientation and shared hardware. |
| Attitude | Basic wheel set, redundant wheels, wheel set with thruster unloading | Pointing error, slew time, momentum capacity and unloading authority; momentum dumps reserve propellant and interrupt incompatible observations. |
| Redundancy | Single string, redundant flight computer, redundant command and data path | Identify which faults each can isolate, switchover time/load, common-mode risks; count actual duplicate hardware. |
| Storage | Basic recorder, larger recorder, protected/mirrored recorder | Usable bytes, write/read rates, correction capability and recovery behavior; enforce packet capacity, charge mass/power and record data discarded on overflow. |

Engineering references: [NASA Small Spacecraft Technology](https://www.nasa.gov/smallsat-institute/sst-soa/) for subsystems, [LRO instruments](https://science.nasa.gov/mission/lro/spacecraft-and-instruments/) for thermal, topographic and neutron observations, [Lunar Prospector](https://science.nasa.gov/mission/lunar-prospector/) for indirect hydrogen evidence. Use mission-specific geometry and station schedules only after sourcing and versioning them. A shadowed target and an orbiter in eclipse are separate conditions.

## Candidate events

Evaluate triggers at named, versioned segment boundaries. Thresholds, duration, resource debits, packet priority and fault profiles must be explicit scenario data. These are proposed transition rules, not numerical specifications. Omit an event until its inputs and consequences are modeled. Radio lines below are fictional.

| Event ID · Phase | Trigger and state read | Choice → deterministic result; causal trace | Sample radio |
|---|---|---|---|
| `trajectory_correction` · transfer | Scheduled navigation checkpoint; predicted insertion error above tolerance; reserve and burn time | Correct → debit maneuver reserve and apply modeled burn; defer → retain error and test insertion gate. Trace route, maneuver authority, error and reserve. | Reyes: “We’re off course. Can we spare a correction?” |
| `array_deployment` · commissioning | Versioned actuator fault and deployable hardware; latch state, energy and remaining attempts | Retry → debit attempt energy and recheck scenario response; lock partial → use partial generation for subsequent segments. Trace array geometry and latch profile. | Amina: “One wing hasn’t latched.” |
| `eclipse_deficit` · survey | Predicted energy below selected timeline load; state of charge and load priority | Shed instrument load → reduce scheduled collection; continue → run until instrument cutoff or bus cutoff. Trace usable charge, eclipse duration and draws. | Amina: “This pass will run the battery down.” |
| `wheel_saturation` · survey | Predicted momentum exceeds selected wheel capacity; propulsion and observing time | Unload if available → debit propellant/time, restore margin; pause → drop observations that require stable pointing. Trace wheel capacity, disturbance and actuator. | Amina: “The wheels are running out of room to steer.” |
| `thermal_warning` · survey | Predicted instrument temperature crosses its allowed range | Pause and condition → debit time and heater energy as applicable; skip → preserve resources, forgo planned packets. Trace temperature, thermal package and window. | Amina: “The sensor is outside its temperature range.” |
| `calibration_drift` · survey | Versioned calibration residual beyond instrument tolerance | Recalibrate → debit time and energy, reread residual; flag → retain provisional data at lower evidence quality. Trace instrument, calibration profile and residual. | Chen: “The reference reading has drifted.” |
| `hydrogen_signature` · survey | Valid neutron packet exceeds scenario evidence threshold for hydrogen | Cross-check when another valid observing opportunity exists → schedule corroboration; report candidate → retain indirect evidence only. Trace footprint, modality and uncertainty. | Chen: “We have a hydrogen signal. What else can we measure?” |
| `conflicting_measurements` · survey | Co-located usable observations disagree under the versioned evidence rubric | Revisit if feasible → acquire an independent sample; report unresolved → retain both packets and attach disagreement finding. Trace overlap, instrument quality and rubric. | Chen: “The instruments tell different stories.” |
| `extra_observation` · survey | Scheduled optional window and positive energy, pointing and storage margins | Accept → debit resources and record modeled packets; decline → leave margins intact. Trace window geometry and resource gates. | Reyes: “There’s time for one more pass if you want it.” |
| `storage_warning` · survey | Predicted next observation exceeds free recorder space | Evict eligible low-priority packets in stable order → free bytes and log each loss; skip capture → preserve existing packets. Trace recorder and packet priorities. | Amina: “We don’t have room for the next pass.” |
| `memory_error` · survey | Scenario fault at a fixed write checkpoint; packet and correction capability | Recover if protected → restore packet and debit recovery time; isolate → mark packet unreadable and prevent transmission. Trace fault profile and protection state. | Amina: “A recorder block failed its integrity check.” |
| `weak_downlink` · downlink | Window open; modeled link margin only supports reduced rate | Lower rate and send prioritized packets → debit window time using fallback link; reserve for next contact → retain packets and record no current return. Trace geometry, antenna gain and station profile. | Reyes: “The ground station can hear us, but only at a slower rate.” |
| `missed_window` · downlink | Scheduled contact ended before acquisition; remaining windows and stored packets | Schedule next feasible contact → keep packets and consume modeled wait resources; end session → unsent packets do not count as returned. Trace schedule and acquisition delay. | Reyes: “The station has set. Do we have another contact?” |

## Lifecycle, replay and integration

1. Engine validates mission, model, catalog, design, route and choice IDs before simulation. Compute feasibility and stable rule findings. Keep unapproved options out of the versioned catalog. The UI receives display values and choices from the engine, with the renderer mapping part IDs to shapes.
2. Advance the published segment order and evaluate rules against the current state. An eligible event becomes triggered only when its rule passes and the versioned per-mission optional-event cap allows it. Rank ties by configured priority and stable occurrence ID. Keep mandatory events outside that cap; preserve the reasons for incidents skipped by the cap.
3. A triggered event exposes only applicable choices with consequence previews. For live play, stop on the pending occurrence; a valid choice resolves it exactly once. Apply the state delta before evaluating later events. Check bounds, reject impossible transitions, and retain before/after snapshots with stable finding, rule and source IDs. Record the result in sequence for debrief and comparisons.
4. Run playback and counterfactuals through the same pure resolver. No timers, random rolls, network data or ambient time. Replay input must include scenario, model and catalog versions plus the ordered choices keyed by occurrence ID. For a branch, discard inherited choices only when their occurrence no longer triggers; pause for a branch choice when a new required occurrence appears. Record these differences. Keep v0.1 saves readable with their original model; do not silently recalculate or upgrade them.
5. Require repeatable serialized results, threshold and cap boundary tests, invalid-choice rejection, stable ordering, conservation of energy/fuel/bytes across transitions, and science scoring only for usable data returned. Verify that UI visual states follow engine results, and that changing one component or choice produces an explainable divergence in Multiverse.
